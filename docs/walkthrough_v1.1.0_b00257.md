## 2. 근본 원인 분석 (Root Cause Analysis)

### 2.1. 왜 '내 개인보관소'가 2개로 보였는가?
- `v1.1.0-b00253`에서 보관소 퇴장 후 개인 보관소 실종을 방지하기 위해 `getMyGroups`에 `SELECT * FROM groups WHERE owner_id = userId` 쿼리를 추가했습니다.
- 하지만 과거 테스트나 세션 생성 과정에서 생성되어 `groups` 테이블에 남아있던 **멤버 0명·데이터 0개짜리 고아(유령) 보관소(`wii-o8uteo`)**까지 `ownedData`로 함께 조회되었습니다.
- 기존 코드는 사용자가 소유한 보관소를 무조건 모두 `myGroups` 목록에 넣었기 때문에, 두 보관소 모두 `owner_id === user.id`로 판정되어 **'내 개인 보관소'라는 이름으로 2개가 동시에 노출**되었습니다.

### 2.2. 왜 '내 보관소 공유 코드'만 다른 코드로 보였는가?
- `SettingsTab.tsx`의 '내 보관소 공유 코드' 영역은 `myGroups.find(g => user && g.owner_id === user.id)`로 보관소를 찾았습니다.
- `myGroups` 배열의 첫 번째 요소에 유령 보관소(`wii-o8uteo`)가 먼저 위치하면서, 실제 사용 중인 보관소 코드가 아닌 **유령 보관소의 엉뚱한 코드**가 노출되었습니다.
- 반면 '보관소 복구 · 기기 변경' 화면은 현재 화면에 로드된 활성 보관소(`activeGroup?.code`)를 직접 참조하고 있었기 때문에 정상 코드가 표시되어 **두 화면 간 코드 불일치 현상**이 발생했습니다.

## 3. 조치 및 개선 사항 (`v1.1.0-b00257`)

1. **`getMyGroups` 단일 개인 보관소 보장 및 유령 보관소 자동 정리 (Self-Healing)**
   - `group_members`에 이미 등록된 정상 개인 보관소가 존재할 경우, `groups` 테이블의 미등록 유령 보관소를 목록에 추가하지 않도록 차단했습니다.
   - 어떤 예외적인 상황에서도 `rawGroups` 내에 사용자가 소유한 보관소는 **현재 활성 보관소(`wii_active_group_id`) 단 1개만 남도록 완벽히 중복 제거(Deduplication)** 처리했습니다.
   - 멤버가 0명인 유령 보관소는 백그라운드에서 DB 상에서 영구 파기하여 데이터베이스를 스스로 자가 치유(Self-Healing)하도록 구축했습니다.

2. **`SettingsTab` 공유 코드 & 복구 코드 참조 일원화**
   - `myOwnGroup` 결정 시 현재 활성 보관소가 내 소유라면 활성 보관소를 최우선으로 확정하도록 수정했습니다.
   - 가족 동기화 화면의 `내 보관소 공유 코드`와 복구 화면의 `내 보관소 고유 복구 코드`가 **동일한 `myOwnGroup?.code`를 100% 일관되게 참조**하도록 통일했습니다.
